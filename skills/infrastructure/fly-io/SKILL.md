# Fly.io

## Purpose

This skill covers deploying and operating applications on Fly.io: apps
and Machines, `fly.toml` configuration, Docker-based deploys, multi-
region placement, volumes, Managed Postgres, secrets, custom domains
with TLS, monitoring, scaling, and rollbacks. It produces a Fly.io app
that deploys with zero downtime, runs close to its users, and can be
rolled back to a previous image.

## When to Use

- Launching a new app on Fly.io with `fly launch`.
- Writing or changing a `fly.toml` configuration.
- Deploying a Docker-based app with `fly deploy`.
- Running an app in multiple regions or scaling Machines up and down.
- Setting secrets with `fly secrets`.
- Creating and mounting a persistent volume.
- Provisioning Managed Postgres and attaching it to an app.
- Adding a custom domain and TLS certificate.
- Debugging a failed deploy, a failing health check, or a crashing
  Machine.
- Rolling back to a previous release image.

## When Not to Use

- Deploying to Vercel, Railway, or Render — use `vercel`, `railway`, or
  `render` instead.
- Self-hosting on your own server — use `self-hosted-vps`.
- Container image authoring in depth — use `docker`.
- General deployment strategy — use `deployment`.
- Designing the CI pipeline that deploys — use `github-actions` or
  `ci-cd`.
- Monitoring strategy beyond Fly.io's built-in logs and metrics — use
  `observability`.

## Prerequisites

- A Fly.io account and `flyctl` installed and authenticated
  (`fly auth login`, or `FLY_API_TOKEN` for non-interactive use).
- A `Dockerfile` in the project (or a project `fly launch` can detect);
  Fly.io builds and runs Docker images on Machines.
- The application listens on the port declared as `internal_port` in
  `fly.toml` (default `8080`), on all interfaces.
- A `fly.toml` in the project root, normally generated by
  `fly launch` and kept in version control.
- Current stable as of 2026-11-20. Managed Postgres (MPG) is Fly.io's
  fully managed Postgres offering; the older self-managed Fly Postgres
  clusters (created with `fly postgres create`) still exist but run as
  Fly apps you operate yourself. Prefer MPG for new projects.

## Required Workflow

1. Confirm the application builds and runs locally from its Dockerfile,
   and listens on the intended internal port.
2. Install and authenticate flyctl:
   `curl -L https://fly.io/install.sh | sh` (or `brew install flyctl`),
   then `fly auth login`.
3. Launch the app from the project directory: `fly launch`. Accept or
   adjust the generated `fly.toml`; use `fly launch --no-deploy` to
   review the config before the first deploy, and `fly launch --db mpg`
   to provision Managed Postgres as part of the launch.
4. Set secrets with `fly secrets set KEY=value` — never put secrets in
   `fly.toml`, which is committed to version control.
5. Create a Managed Postgres cluster when the app needs a database
   (`fly mpg create`), then attach it (`fly mpg attach <cluster-id> -a
   <app>`), which sets the `DATABASE_URL` secret on the app.
6. Create a volume when the app needs persistent local storage
   (`fly volumes create <name> --size <gb> --region <code>`), and mount
   it in `fly.toml` under `[mounts]`, in the same region as the
   Machine that uses it.
7. Deploy with `fly deploy` and watch the output; confirm the health
   checks pass and the `*.fly.dev` URL responds over HTTPS.
8. Add a custom domain: `fly certs add <domain>`, set the DNS records
   Fly.io shows (CNAME for a subdomain, A/AAAA records for an apex
   domain), and confirm with `fly certs check <domain>`.
9. Record the rollback path before the first production deploy:
   `fly releases --image` lists release images, and
   `fly deploy --image <image> --rollback` redeploys a previous image.
10. Run at least two Machines for anything user-facing, so a single
    Machine failure or a deploy does not take the app down.

## Implementation Standards

- `fly.toml` is the source of truth for the app's deployment config
  and is kept in version control; secrets never appear in it.
- Use the rolling deploy strategy (the default) for zero-downtime
  deploys; use `immediate` only when downtime is acceptable, and
  `canary` or `bluegreen` when a gradual or fully verified rollout is
  required.
- Run database migrations as a release command (`[deploy]
  release_command`) so they run in a temporary Machine before the new
  release starts serving traffic; keep migrations backward compatible,
  because a rollback redeploys the old image, not the old schema.
- Define real health checks (`[[http_service.checks]]`) that reflect
  readiness, including the database connection where the app depends
  on one; a deploy that fails its health checks stops the rollout
  instead of replacing every Machine with a broken version.
- Treat a volume as a single-host disk: it lives on one host, attaches
  to one Machine, and is not replicated. Data that must survive a host
  failure needs an off-platform backup in addition to Fly.io's
  snapshots.
- Keep `[[vm]]` sizing in `fly.toml` when the app has explicit size
  requirements; each deploy applies those values and overrides
  `fly scale vm`.
- Handle shutdown gracefully: Fly.io sends `kill_signal` (default
  `SIGINT`) and waits `kill_timeout` (default 5 seconds, up to 300)
  before forcing the Machine down.
- Prefer the private network for service-to-service calls: apps reach
  each other over `.internal` DNS and Flycast addresses, and Managed
  Postgres is reachable only over the private network.

## Best Practices

- Use `fly launch --no-deploy` on a first deploy so `fly.toml` can be
  reviewed (regions, ports, checks, auto-stop settings) before
  anything goes live.
- Run two Machines in the primary region for user-facing apps; the
  first deploy creates two Machines for redundancy when services are
  defined.
- Use `auto_stop_machines = "stop"` with `auto_start_machines = true`
  and `min_machines_running = 0` for apps that can scale to zero, and
  `min_machines_running = 1` (or more) when the app must always be up;
  never scale a volume-backed single-Machine app to zero unless the
  cold start is acceptable.
- Keep the Docker image small with a multi-stage build; smaller images
  deploy faster and start faster.
- Use `fly status`, `fly machine list`, and `fly checks list` to see
  what is actually running before changing configuration.
- In CI, deploy with a scoped deploy token (`fly tokens create deploy`)
  stored as a repository secret and passed as `FLY_API_TOKEN`; never
  use a personal login token in automation.
- Record the deployed image reference before a risky deploy so a
  rollback does not depend on remembering it later.

## Security Considerations

- Never put secrets in `fly.toml`, the Dockerfile, or the image; use
  `fly secrets set`, which stores them encrypted and never shows
  values back (`fly secrets list` shows names only).
- Managed Postgres clusters are reachable only over Fly.io's private
  network; reach them from a local machine with `fly mpg proxy` or
  `fly mpg connect`, never by exposing the database publicly.
- Restrict who can run `fly secrets set` and `fly deploy` for a
  production app; anyone with deploy access can read the app's
  environment through the code they deploy.
- Use scoped deploy tokens in CI with the shortest practical expiry;
  rotate a token immediately if it was ever exposed.
- Enable `force_https = true` in `[http_service]` so plain HTTP
  requests redirect to HTTPS at the edge.
- Make the application trust the `X-Forwarded-Proto` header Fly.io
  sets; the proxy terminates TLS and forwards plain HTTP to the app,
  so app-level HTTPS redirects cause redirect loops.
- Keep the base image updated; a deployed Machine keeps running the
  image it was built with until the next deploy.

## Performance Considerations

- Put Machines in the regions closest to the users; Fly Proxy routes
  each request to the nearest healthy Machine.
- Keep the database in the same region as the app's primary Machines;
  cross-region database calls add latency to every request.
- Use the pooled `DATABASE_URL` that `fly mpg attach` sets (it routes
  through PgBouncer) instead of opening a new connection per request.
- Tune `[http_service.concurrency]` soft and hard limits to the app's
  real capacity; when the soft limit is hit, Fly.io starts additional
  Machines (when autoscaling is configured) instead of overloading
  one.
- Scale-to-zero saves money but adds a cold start on the first request
  after idle; keep `min_machines_running = 1` or higher for
  latency-sensitive apps.
- Watch Machine memory: a Machine that runs out of memory is killed
  and restarted, which looks like an intermittent outage; size `[[vm]]
  memory` from observed usage, not guesses.

## Common Mistakes

- Putting secrets in `fly.toml` — the file is committed to version
  control; secrets go in `fly secrets`.
- Assuming a volume is replicated — it lives on one host, so a host
  failure loses data that has no off-platform backup.
- Creating a volume in a different region from the Machine — the
  Machine cannot mount it; create the volume in the app's region.
- Running two Machines against one volume-backed SQLite database —
  only one Machine can mount a volume, and the second Machine fails
  or corrupts the data.
- Forgetting that `fly deploy` applies `[[vm]]` from `fly.toml` —
  manual `fly scale vm` changes are overwritten by the next deploy.
- Setting `min_machines_running = 0` on an app that must always answer
  — the first request after idle waits for a cold start.
- Deploying with `auto_stop_machines` on a worker or a cron-like
  process — stopped Machines do not run background work.
- Rolling back with `fly deploy --image` and expecting it to undo a
  migration, a `fly.toml` change, or a secret change — it redeploys
  the old image only.
- Letting the app redirect HTTP to HTTPS itself — Fly.io already
  terminates TLS and forwards HTTP; use `force_https` and trust
  `X-Forwarded-Proto`.

## Examples

Install flyctl, authenticate, and launch an app with Managed Postgres:

```bash
curl -L https://fly.io/install.sh | sh
fly auth login
fly launch --db mpg
fly deploy
```

A production `fly.toml` for a web service:

```toml
app = "my-app"
primary_region = "iad"
kill_timeout = 10

[build]
  dockerfile = "Dockerfile"

[deploy]
  strategy = "rolling"
  release_command = "npm run db:migrate"

[env]
  NODE_ENV = "production"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 1

  [[http_service.checks]]
    grace_period = "10s"
    interval = "15s"
    method = "GET"
    path = "/health"
    timeout = "5s"

[[vm]]
  memory = "512mb"
  cpu_kind = "shared"
  cpus = 1
```

Secrets, volumes, and scaling:

```bash
fly secrets set SESSION_SECRET="$(openssl rand -hex 32)"
fly secrets list

fly volumes create app_data --size 1 --region iad

fly scale count 2 --region iad
fly scale count 1 --region lhr
fly scale vm shared-cpu-2x --memory 1024
```

Custom domain and TLS:

```bash
fly certs add app.example.com
fly certs check app.example.com
```

Rollback to the previous release image:

```bash
fly releases --image
fly deploy --image registry.fly.io/my-app:deployment-01HXXXXX --rollback
```

Check status, logs, and Machine health:

```bash
fly status
fly logs
fly machine list
fly checks list
```

## Validation Checklist

- [ ] The app builds from its Dockerfile and `fly deploy` succeeds.
- [ ] Health checks pass on every Machine (`fly checks list`).
- [ ] The `*.fly.dev` URL and the custom domain both respond over HTTPS.
- [ ] Secrets are set with `fly secrets`; none appear in `fly.toml`,
      the Dockerfile, or the repository.
- [ ] At least two Machines run for a user-facing app.
- [ ] The database is attached and reachable (`DATABASE_URL` is set by
      `fly mpg attach`).
- [ ] Volumes are mounted in the same region as their Machines, with a
      backup plan for critical data.
- [ ] The rollback path is known: `fly releases --image` and
      `fly deploy --image <image> --rollback`.

## Expected Deliverables

- The Fly.io app deployed and verified over HTTPS, with `fly.toml`
  committed to the repository.
- Secrets set, the database attached, and volumes mounted where needed.
- The custom domain configured and verified, when one is used.
- Documentation of the deploy, scaling, and rollback steps for the app.
